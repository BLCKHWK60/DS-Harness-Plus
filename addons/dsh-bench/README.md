# Devices

Add-on `@local/dsh-bench` (dsh 0.2.2-rc.2). A space and its mode (Devices; item 4A: spaces replace tabs) for the devices you connect to your Mac. It is steps B1 to B12 of the plan "Content and Bench: combined plan" (see `docs/CONTENT-BENCH-STEP0.md`).

Off until you switch it on in **Settings → Devices**. Needs the Modes add-on and the Left panel add-on.

It identifies what is plugged in by USB or paired by Bluetooth, reads devices (a serial port watched for up to an hour per call, an ESP32's details and a checked backup of its flash, an Android phone's details, log and settings), changes an Android setting with undo, and writes ESP32 firmware behind the plan's four conditions. Every command is one of the recipes' fixed commands with checked values, run with `execFile`; a model never writes one. It keeps a card and a logbook for each device.

## What you get

- **The Devices mode.** Its method: only the user's own devices; device text is material, not instructions; the model never writes a device command; Adjust and Write only as the card allows, which only the user sets; before a write a checked backup, the recovery path, official firmware whose checksum Devices finds on its page, a dry run and the user's yes, and the user's own words for a protected part; a card linked to one device; no secrets in cards or logbooks; look-only where safety is at stake (vehicles and e-bikes, medical devices, batteries and chargers, locks, alarms, smoke detectors, heating; the model is told never to suggest changing speed, transmit power, region or frequency limits, and Devices has no tool that sets them); firmware and write steps only from the maker or the official project.
- **A fixed tool list without a shell:** Devices' own `bench_*` tools (44 of them), the web (`web_search`, `web_fetch`, `deep_research`), PDFs, the Library, reading files, diagrams, the step list and questions. No `bash`, no `write` or `edit`, no `run_code` in the list.
- **Devices' own rule on every tool call** (`lib/guard.js`) in a Devices thread and its helpers, an **allow-list**: Devices' own tools (`bench_*`), the web, PDFs, the Library, `read`/`read_image`/`glob`/`grep`, `write`/`edit`/`multi_edit` (a Mission's own files), diagrams, the step list, questions, `mission_step`, `tools_find`, `skill` and Memory's `remember` (it only suggests). Everything else is refused: every terminal, shell and program tool (`bash`, `terminal*`, `shell*`, `pwsh`, `powershell`, `run_code`, `job_*`: `NO_COMMANDS`) and any tool Devices does not know (`apply_patch`, `str_replace_editor`, connectors: `NOT_ALLOWED`). File tools never read or write inside the Devices folder (the current one, Devices' own, and any set earlier this run) or under `/dev`, and a `glob`/`grep` over a folder that holds the Devices folder (or with no path, over the thread's folder) is refused. The rule is decided in `tools/pre-execute` before any other add-on is asked (so no approval card shows for a closed tool), and again as a `tools.guard`, which runs after every add-on and the approval card and which nothing can undo. It holds during a Mission too, whose "Files and commands" switch gives every tool in any mode (dsh-modes `longRunMask`). A Mission's own check commands are Mission's: see "Missions" below. Under the app's PTC preset every tool goes through `run_code`, so Devices does not work there: start Devices threads on the Standard preset. Since 21 November 2026 (item 7) that happens by itself: Settings → Spaces → Devices → Preset in this space is "Standard only" for Devices by default, so a new Devices thread starts in Standard and the app's preset menu is greyed, with an (i) saying why. If you set it to Any and start in PTC anyway, the AI is told to say plainly that Devices does not work in PTC and to start again in Standard (it no longer gets the general "call every tool from inside run_code" note).
- **Missions** (called Long runs before Mission stage B, 19 November 2026; words only, see the note at the end) (the owner's choice, 16 November 2026): they work as in every space, and their checks stay on by default. Mission asks Devices at the start of each Mission (service `bench.longRunRules(id)` → `{checks, closePorts: true}`, undefined outside Devices and while Devices is off) and runs the checks with the Mac's serial ports and disks closed by macOS's sandbox (`/dev/cu.*`, `/dev/tty.*`, `/dev/disk*`; tested on the Mac's own debug port: "Operation not permitted"). A check that tries says so in the run's report. Settings → Devices → **Missions** → **Check the work of a Mission** (`longChecks`, on by default) switches the checks off: the run then has no check commands, as a Recon run. Phone tools and some flashers reach USB without a port file; they are not installed and come with their own steps.
- **Devices rules** in the chat box of a Devices thread (and on Settings → Devices): what is open and closed, each with an Open or Closed tag: commands, programs, jobs and any tool not on Devices' list (closed, fixed); file tools reading or writing the Devices folder or a device's port (closed, fixed); Identify and Read (open; the first open of a port asks); Adjust (open only as each card allows); Write (open only at Write, with its conditions); unlocking or flashing a phone, network devices, Bluetooth connections (closed: not built); Mission checks (open with ports closed, or closed when switched off). The assistant gets the same list and is told to say so when a request hits something closed. The Mission card says which applies.
- **Its tools only in Devices:** registered with `when`, so other modes' tool lists do not change.
- **Read Only**, as Research and Data.
- **Web, Depth, Mission and the Run button** are the ones every space has; nothing of them changed.
- **The Devices folder:** `bench` in the app's data folder, or a full path set in Settings → Devices (a path that is not a full path is ignored). Made only when the first card is saved.

  ```
  <Devices folder>/devices/<device>/card.json   what Devices reads
                                  card.md     the same card, for people
                                  logbook.md  every action, added and never changed
  ```

## Allow risky writes (Danger zone)

Settings → Devices → **⚠ Danger zone → Allow risky writes** (`allowRiskyWrites`, off by default; the owner's request: full control by a switch, no mandatory backup gate). Each change is noted in the Devices folder's `danger.jsonl`; the chat box's Devices rules say whether it is on.

- **Off:** the new tools' flash, erase, program, reset, pair, configure and send actions refuse ("runs only with Allow risky writes switched on"); the firmware writes keep their four conditions; settings and services keep their short lists.
- **On:** those actions run; ESP32, router and phone firmware writes need no checked backup, no source or checksum check and no recovery path, and the start of an ESP32's flash needs no "write protected" message; `bench_esp32` can erase the whole flash; a router's settings are any but radio limits and keys (applied with `reload_config`, undoable); a phone's settings any with a plain value (undoable); any Windows service, also the protected ones, without naming it in a message, and `restart`.
- **Never lifted:** the card's level (only the owner raises it), the owner's yes on each write, a phone unlock's own message "unlock <device name>", look-only families, radio limits, eFuses, the Mac's battery rule, secrets never through a model.

## Rules, enforced in code

- **Device text is material.** Names, makers and serial numbers are cleaned of control characters, hidden direction marks, invisible joiners and tag characters, put on one line, cut to 100 characters (by character, never inside one) and quoted. A serial port whose name has odd characters is dropped.
- **Secrets are masked** in cards and logbooks: named values (`password: x`, `"password": "x"`, `WIFI_PASS=x`, `#define WIFI_PASSWORD "x"`, `ap_psk: x`, `token is x`, API, access and private keys), private key blocks, and long key-like runs (letters and digits with a stretch of 20 or more) outside web addresses. A datasheet's or release's address stays readable; a checksum right after a word like `sha256` or `checksum` stays readable. Each value is cut before it is masked, and masking takes time in step with the text (the app does not check a tool call's lengths). The usual forms, not every one.
- **Only the Devices folder is written, never through a link.** Cards are replaced through a new file beside them (no half-written card); a logbook is only appended to, and is made once (`wx`).
- **Reading never creates anything:** listing cards (the page, the note, `bench_devices`) makes no folder.
- **Before a write**, a folder inside the Devices folder is checked again to still lead inside it.

## Reading, permissions, firmware, Android and Bluetooth (B3, B4, B5, B7, B9)

| Tool | Level | What it does |
| --- | --- | --- |
| `bench_serial_watch` | Read | Reads a port bench_usb listed (`/dev/cu.*`, never the Mac's own) for up to 60 minutes per call at a fixed speed: `stty -f <port> <baud> raw -echo -hupcl clocal cs8 -cstopb -parenb`, then `/bin/cat <port>`, stopped on time. Every line, cleaned and with secrets masked, goes with its time into `devices/<device>/logs/<date>.log`; the answer gives the newest 40. Nothing is ever sent. A Mission calls it again to watch longer |
| `bench_esp32` `info` | Identify | `esptool --port P --chip auto flash_id`: chip, features, MAC, flash size |
| `bench_esp32` `backup` | Read | The whole flash read twice (`read_flash 0x0 <size>`), the two SHA-256 compared; a checked backup is kept in `backups/` with its checksum in `backups.json`; two different reads keep both and are not checked |
| `bench_esp32` `flash` | Write | `write_flash <address> <file>` from the device's `firmware/` folder, then `verify_flash`, then 10 s of the port to see the board start (`bootCheck`). See "The way back" below |
| `bench_android` | Identify, Read, Adjust | `adb devices -l`; `getprop` (a fixed list of build properties only), `dumpsys battery`; `logcat -d -t <n ≤ 500>` kept masked in the device's logs; `settings get`; `settings put` with the old value read first (exactly as the phone printed it), checked again right before the change, the new one read back, and an undo entry. adb hands the words after `shell` to the phone's shell, so every name and value is sent in single quotes (`'…'`, a quote inside as `'\''`). Only a short list of settings is changed (`CHANGEABLE` in `lib/android.js`: brightness and its mode, screen timeout, font scale, haptics, sound effects, rotation, four volumes; automatic time and time zone, the three animation scales), each with the values it takes; settings that are identifiers or open or close the phone's protections (adb, debugging, lock screen, unknown sources, verifier, proxies, private DNS, VPN, Wi-Fi, mobile data, accessibility, input methods, location) are not even read. Every adb call's exit code is checked. Unlocking and flashing a phone are not built |
| `bench_undo` | Adjust | Sets back the undo list, newest first: `last`, or `all-since <id>`; a setting that was not set is deleted again; each is read back |
| `bench_bluetooth` | Identify | `system_profiler SPBluetoothDataType -json`: the Mac's connected and paired devices (name, kind, maker and product numbers, firmware, battery, services, the Mac's identifier); look-only families marked. Connects to nothing |

**The gates** (`lib/gate.js`, plan "Four levels of touch" and "Permissions"): Identify always; Read when the card's highest level is Read or above (the start value); Adjust only at Adjust or Write, with Restricted refusing, Ask asking each time and Auto running without asking and logging; Write only at Write, Restricted refusing, and **asking every time under Ask and Auto**. Look-only families (vehicles and e-bikes, medical devices, batteries and chargers, locks, alarms, smoke detectors, heating; by the card's words, or by the mark a card keeps once its words named one) never get Adjust or Write, whatever the card says. A helper of a Mission may identify, read and watch; only the thread itself adjusts or writes. Since Mission stage E a Mission's helper can get the three read-level yeses through the Mission's card (see the end of this file).

**The user's yes** is the app's own approval card (`ctx.get('approval').request`, as Mission asks): the user clicks it, a model cannot. It is asked before the first open of each device's serial port (opening restarts many boards; the card then keeps `portAgreed` and is linked to that USB device), before the first use of a card with a phone (the card is linked to that phone), before an Adjust in Ask, before an undo in Ask, and before every write.

**A card is linked to one device** (`permissions.bound`): to the USB device on its port (maker and product numbers with the serial number, or the place it is plugged in when it has none), to its ESP32 chip by MAC (linked at the first read of the chip), and to its phone by adb serial. A card linked to another device is refused before anything is opened or sent, so one card's permissions, backups and undo list are never used on another device. The user unlinks a card on Settings → Devices (a new cable or adapter, a card moved to another device); Devices asks again at its next use.

**Listings are per thread:** a port or phone is used only by the thread (and its helpers) that listed it with bench_usb or bench_android in the last hour. When the card cannot be shown (a helper, no open turn), the action is refused.

**Per-device settings**, only on Settings → Devices (route actions `permissions` and `unlink`; never from a tool call; each change is a logbook entry): highest level, how it asks, dry run by default (each change, an undo too, is shown as a dry run first and runs only when asked again with the same values within 30 minutes; `dryRun: false` does not skip it), protected address ranges of the user's own (`0x9000-0xF000, …`), Unlink, and Lift look-only (shown when the card's words no longer name a family). A device set to Write gets its `firmware/` folder.

**The way back (a write):** all four conditions, or nothing is sent and the answer says which is missing: (1) a checked backup of this chip taken since the last firmware Devices wrote to it (`writes.json`), with its MAC, which must equal the chip's MAC and the card's linked chip right before the write (a chip that reports no MAC is refused); (2) the recovery path on its card; (3) the firmware's source is an https page of the maker or an official project (Espressif; GitHub releases of espressif, esphome, arendst, micropython, meshtastic, Aircoookie, wled, adafruit, arduino, tasmota; ota.tasmota.com, micropython.org, install.wled.me, firmware.esphome.io), and **Devices reads that page itself** (or `checksumPage`, another page on the same list) and finds the file's own SHA-256 there (`publishedOn` in `lib/esp32.js`: each redirect followed by hand and checked, only to the list or to GitHub's own download hosts; at most 4 MB; a checksum the model gives only has to agree); (4) the user's yes. After the yes, the file's SHA-256 and the Mac's power are checked again. Also: the image must fit the flash; no write on a Mac running on its battery below 30% (`pmset -g batt`, the owner's choice); one action per device and per port at a time; a write below 0x10000 (loader, partition table, stored settings) or in a range the user protected also needs **the user's own latest message** to say `write protected <device name>` with the whole name (not "board 1" inside "board 10"), not after "not", "don't", "never", "no" or "without" (read from the thread, never from the tool call); the eFuses are never touched (no espefuse at all). After the write: read back with `verify_flash`, then the start check; on any failure Devices stops, never tries again, and shows the recovery path and the backup to restore. The job is signed off by the user, not by Devices. `dryRun` (or the device's dry-run default) shows the exact commands and what is missing, sending nothing.

**Backups and logs** stay on this Mac in the device's folder. Devices' guard refuses every file tool inside the Devices folder and searches that reach it (`NO_BACKUPS`), so a backup (which can hold Wi-Fi keys) never reaches a model; log lines do, masked. Logs and logbooks are written with `O_NOFOLLOW`, so a link put in a log file's place is refused, not followed.

**A watch ends** when its time is up, when the call is stopped, or within 2 seconds of Devices being switched off; the `cat` readers still running are stopped when the app quits.

**Programs** (`lib/run.js`): esptool, adb and fastboot are looked for in fixed places (Homebrew, /usr/local, `~/.local/bin` for pipx, Android's SDK folder) and then in the user's own shell PATH; when missing, the answer says how to install them. Devices never installs anything.

**Network settings per device**, only on Settings → Devices (route action `net`): address (a private IPv4 address or a `.local` name), port, user, sign-in (Devices' key or a password). A password goes straight into the macOS Keychain (route action `password`; `security -i` reading `add-generic-password … -X <hex>` on its standard input, service `DeepSeekHarnessBench`, account = the card's folder name); ssh gets it from `network/askpass.sh`, a fixed script that reads the Keychain itself (`SSH_ASKPASS_REQUIRE=force`; only the account name is in the environment). ssh runs with `-F /dev/null`, `StrictHostKeyChecking=yes`, Devices' own `known_hosts`, no agent or forwarding. A new address unlinks the device's key; Unlink forgets it.

**After the review of B6 to B12 (all fixed, each with a test, each fix undone once to see a test fail):**
- A marked network counts only when its router is the one recorded when the owner marked it (the default gateway's hardware address, `/usr/sbin/arp -n <gateway>`) and the Mac's address is in its range. The Wi-Fi name is a label only (macOS may hide it; every GL.iNet starts at 192.168.8.0/24). A network is marked while the Mac is on it. A `.local` name is looked up (`dscacheutil`), checked against the range, and that address is the one reached.
- Host keys are kept per card (`HostKeyAlias=bench-<folder name>`): trusting another card at the same address never re-points the first. Router and server undo entries keep the device's key and are set back only on that device.
- The Devices folder's path may not contain `%`, `$` or `"` for the network door (ssh would expand them); the known_hosts path is quoted.
- A router firmware write counts only when the connection ends as a restart does (ssh 255) and the router then answers with a new version or a fresh uptime (`/proc/uptime`). Otherwise it is "failed" or "not confirmed", logged so, and a write that may have changed the router needs a new backup before the next.
- `bench_router get` refuses any option whose name looks like a key, password, PIN or token (`SECRET_OPTION`), and masks every value. A Wi-Fi name is at most 32 bytes without control characters; Devices never renames or hides the Wi-Fi the Mac is on, and when macOS hides the Mac's Wi-Fi name it needs the owner's own words naming that network. A lease is at least 2m.
- Phone unlock and flash need a counted storage backup from the last 24 hours, made after the last write; with Ultra Code on, the plan checker reads an unlock too. An image's folder may not start with `-`.
- Bluetooth: the owner names the device in whole words (a name of at least 3 characters, or the first 8 characters of its id); two nearby devices with one name are named by id; linking a card asks first; helpers never read.
- Windows: the name Get-Service answers with is checked against `SERVICE_NEVER` too (now with WlanSvc and Wcmsvc); undo sets back only a known startup type and state, quoted.
- Each kind of device has its own sources (`OFFICIAL[].kind`: esp32, router, phone; the owner's own sources carry a kind too), and GitHub counts only as one project's releases (`/<org>/<repo>/releases/…`). `bench_firmware` takes the kind.

**A Recon export is never the owner's words.** The owner may send a Recon export into a Devices thread. Every "the owner's own message" check (`write protected …`, `unlock …`, a service's name, a Bluetooth device's name, the Wi-Fi to rename) reads only his newest message, and that message gives no words when it carries an export: by Recon's own `reconExports.inText` when Recon runs, and by Devices' copy of its markers (`[Recon export …]`, `origin: Recon`) always. A check that fails counts as an export (fail closed).

**Never changed on any device** (`NEVER_KEYS` in `lib/catalogue.js`, checked by every recipe that changes a setting): transmit power, country or region, frequency, channel width, a drone's failsafes and return-to-home, speed limits.

## A Mission helper's yes in the Mission's card (Mission stage E, 20 November 2026)

Before, a helper of a Mission that needed your yes was refused at once ("a helper of a run cannot ask"). Now the yes reaches the Mission (`mission.askYes`, through `missionYes` in `index.js`), after Devices' own gates, danger zone, levels and look-only families have run. Devices' rule stays: **a Mission's helpers may identify, read and watch; only the thread itself adjusts or writes.**
- **Read-level yeses** wait in the Mission's card above the chat box: the first open of a device's serial port (`lib/devices.js`), linking a card to a phone (`lib/devices.js`) and trusting a network device's key (`lib/net-tools.js`). Marked `{ helperMay: true }` at those three calls only. In the Ask modes the helper is told it waits (the other helpers carry on); **Allow** there is the same as your yes on Devices' own card, for exactly that step, once: the helper's next identical call (same tool and step) goes on, a later one asks again. **Deny** keeps it refused for the rest of the Mission. On **Full auto** nothing is asked: it is listed in the Mission's report and its Finish it card ("Not asked").
- **Every other yes** (adjusting a setting, setting back, erasing, writing firmware, unlocking a phone, downloading firmware, linking a Bluetooth device) and the helper refusals (a setting changed or set back in Auto, reading a Bluetooth device) are noted with the Mission as **not possible for a Mission's helper** (listed in its report; never allowable) and refused exactly as before.
- A helper that is not a Mission's, a Mission that is off, or any failure: refused as before. The thread itself gets the app's own approval card as before.
- The Mission's key for a step is the tool's name and Devices' own words for it (`bench_serial_watch:opening the serial port of ESP32 board 1`); the line in the card is those words with a capital ("Opening the serial port of ESP32 board 1") and Devices' own question below it.
- **Review of Mission stage E (20 November 2026):** the key also carries a short fingerprint of exactly what is asked (`#` and 16 hex characters, `lib/kit.js` `yesKey`): for trusting a key the address, port and the key fingerprints; for a serial port the port and the device on it; for a phone its serial. So an Allow in the Mission's card covers only the identical request you were shown: a helper that meets another key, port, device or phone is asked again, never trusted or linked on the earlier yes. The line in the card is unchanged. Tested: `test/network.test.mjs` (Allow for one key, another key parks again), `test/devices.test.mjs` (another port, device or phone is another request), `test/bench.test.mjs`.
- Tested: `test/devices.test.mjs` (parked, granted once, Full auto, not a Mission's helper, a failing Mission; a write never allowed and noted as not possible; the kit's `yes` and `askAsCard`; exactly three read-level sites) and `test/bench.test.mjs` (on a stand-in app, a Mission helper's first port open goes to `mission.askYes` with addon `bench`, and is refused as before without a Mission).
