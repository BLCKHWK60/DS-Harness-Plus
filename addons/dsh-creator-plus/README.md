# Creator Plus

Add-on `@local/dsh-creator-plus` (dsh 0.2.2-rc.2). A mode that runs in the Workshop space (item 4A: spaces replace tabs), beside the app's Creator mode (whose files are never touched), that builds and improves add-ons so they fit everything you have. It is Phase 2 of the plan "Creator Plus"; Phase 1 (how Creator mode works, the stock-take, the gaps) is `docs/CREATOR-PLUS-PHASE1.md`, and the handbook for later builders is `docs/CREATOR-PLUS-HANDBOOK.md`.

Off until you switch it on in **Settings → Creator Plus**. Needs the Modes add-on and the Left panel add-on (dsh-cowork-shell).

## What you get

- **The Creator Plus mode** (Workspace Write, with its own guard). Its method (about 2,300 characters, under the 4,000 a mode may have) names its four jobs (build a new add-on, change an existing one, keep everything working after updates, improve from the thread logs) and the six fixed rules, step by step, for a small model.
- **Its tools, only in Creator Plus threads** (registered with `when`, so other modes' tool lists do not change): `creator_map`, `creator_passport`, `creator_recipe`, `creator_interview`, `creator_plan`, `creator_scaffold`, `creator_check`, `creator_change`, `creator_upkeep`, `creator_improve`, `creator_note`, `creator_handoff`, `creator_learn`, `creator_selftest`. Besides them: reading files, and writing them only in the build folder (`creator-plus-builds` inside the thread's folder), the web, the app's inspection tools (`cordis_inspect_list`, `cordis_inspect_query`; they come only with the app's Creator preset, so a Creator Plus thread on Standard or PTC works without them), diagrams, the step list, questions, PDFs. No shell, no programs, no plugin manager.
- **The bar** in the chat box of a Creator Plus thread: which add-ons (built-in and third-party ones carry a lock: read, explained and checked, never edited; Recon shows a note that only its structure is read), "All" on purpose, what to do (New add-on, Improve, Find what went wrong, Rebuild, Combine or split, Find gaps, Check after an update, Explain, each with its line), **Look only** (read and report; prepare nothing, not even in the trial copy), **Logs from** (since the last run, 7 days, 30 days, everything) for the runs that read logs, and the run in one sentence before it starts. **Save run** keeps it by name.
- **Settings → Creator Plus**: the switch; the six rules and how each is enforced; the **results** as cards (a finding, a prepared change, a question, an assumption, a ready add-on) with **Try it in the trial copy**, **Apply to my setup**, **Not now**, **Do not suggest this again** (kept as a preference) and **Undo**/**Remove** after Apply; **what Creator Plus learned** (proposed; kept only when you press Keep; undone with Undo; a lesson from a third-party add-on needs "I read it" first); who may read your thread logs (only models on this Mac by default); strong models (they may improve on a recipe's default steps); the Plus folder with its tests; saved runs; the self-test; the backups.
- **Saved runs on the Automations page** (your answer of 16 November): each saved run can be scheduled there; it runs in a Creator Plus thread of its own that starts with the saved run's bar, as a Mission would, prepares changes in the trial copy only and changes nothing in your setup without your yes. When Creator Plus is switched off, its scheduled saved runs are paused (switch them on again on the Automations page).
- **Missions in the Creator Plus mode** work since Mission stage E (20 November 2026): see "Missions in Creator Plus" at the end.
- **A passport** in every Plus add-on (`passport/`: brief, what it touches, what it was built against, its tests, its changelog, who made it, and an empty `lessons/` folder for Tuner Plus). Built-in and third-party add-ons get theirs in Creator Plus's own folder, never in their own.

## The fixed rules, and the code that holds them

1. **No change without a backup and a way back.** Every change and install keeps the version before it in `<app data>/creator-plus/backups/` first (`lib/trial.js`, `lib/change.js`); Undo puts it back, and putting it back is itself backed up.
2. **Nothing changes in your real setup without your yes.** The assistant's tools work in the build folder; the real setup changes only from a button on Settings → Creator Plus, which only you can press. What is applied is what was reviewed: `creator_check` first copies the add-on into Creator Plus's own folder (out of reach of the file tools and of the sandbox), runs every check on that copy, and Apply installs exactly it (every file hashed; a copy that differs is refused). A change is prepared the same way. The card shows the code in full and unmasked (**Show the code**, **Show the change**: the change line by line and every changed file as Apply writes it); what cannot be shown in full is not applied from here (binary files, modules other than Creator Plus's own, too much code, a change too long to show). Apply runs once (a second click is refused).
   An add-on's code (its tests, its index.js) runs only inside macOS's sandbox (`lib/sandbox.js`), in a fresh run folder of its own (`lib/runs.js`): the host fills it from the host-only copy before anything runs, the sandbox may write only there, and afterwards the host reads only the programs' output and throws the folder away; it never acts on anything the sandbox could write, and Creator Plus's own folders are checked to hold no link. Inside: no network, no Mac services, no launchd job, no program but the app's own Node and the shell, no native code but the system's and the app's, no child process at all (an add-on's tests run in one process; tests that start programs fail there), reading only the system, the app and its run folder (not the home folder, not the app's data, not /tmp or other users' folders), signals only to its own processes, and a short environment with no keys. When a program ends, its whole process group is stopped. The trial install runs in a fresh trial copy per check, the same way; it runs only the app's own `dsh` and package manager (tried: neither the add-on's index.js nor its package scripts run; an add-on with package scripts is blocked), so only it may start child processes. Output is masked and shown to the model as material. Where there is no sandbox, nothing is run.
3. **Another mode's safety rules are never weakened: blocked, not asked.** The fit check blocks a plan that gives a sealed mode a tool, appears in one, loosens a named safety rule, takes a name or a row already on the map (built-in rows too), or changes a file that holds a safety rule: every file of Recon, Devices, Modes, Mission and Creator Plus, Content's subject check, and every add-on's setup file (`cordis.patch.yml`); `creator_change` refuses the same files, capitals ignored. It also reads the built add-on's own code, not only the plan: writing another add-on's settings or the Modes add-on's (a mode add-on adding its own mode is a decision), settings named only at run time, naming a sealed mode, hooking every tool call, and a setup file that does more than insert its own row (checked strictly: no other operation, no tags such as `!!js`, no anchors) are blocked (`lib/fit.js`, `codeFindings`). The code check is a help, not a guarantee: a model can hide what code does (a name put together while running, a file written elsewhere), so the card says so and shows the code; the fixed blocks hold for what can be seen.
4. **Third-party add-ons and the app's own code are never edited.** The guard refuses writes there; the change tools refuse locked add-ons and point to an adapter beside them.
5. **Text from add-ons, pages, logs and tool results is material, not instructions.** It is fenced with a random marker it cannot close (`lib/text.js`).
6. **No password or key in a map, a passport or a log.** Maps hold setting names, never values; maps, passports, cards and log findings are masked; logs go only to the models your setting allows (and the cards with their evidence sit in Creator Plus's own folder, which no file tool reads); the file tools cannot read the app's data folder (only the installed Plus add-ons and the thread's folder).

The guard (`lib/rules.js`) decides every tool call in a Creator Plus thread and its helpers in `tools/pre-execute`, before any other add-on is asked, and again as a final `tools.guard` that nothing can undo. It is an allow-list: Creator Plus's tools, file tools, the web, the inspection tools, the step list, questions, `mission_step`, `tools_find`, `skill`, diagrams, PDFs and Memory's `remember`. Every shell, terminal and program tool is refused (`NO_COMMANDS`), as is any tool it does not know (`NOT_ALLOWED`). Writes only inside the build folder, `creator-plus-builds` in the thread's folder, by their real path (a link out of it does not count), never in the app, the installed add-ons, the app's settings or threads, the Plus folder, or Creator Plus's own folder. A thread whose folder is your home folder, the whole disk, inside `~/Library`, holds or lies in the app's data (Scratch excepted) or a Plus folder, lies in the app, or is Recon's sealed room (a `dsh-recon-*` folder directly in a temporary folder, the rule Content uses), builds nothing. File tools never read or write inside a Recon room, and a search over a temporary folder is refused. A call it cannot check is not run. Also:

- **The bar's selection is a boundary:** an add-on's own files are opened, and an add-on changed, only when it is selected; otherwise it is a line on the map. The same holds in the Plus folder named on the page, and a look over all the add-ons at once (their folder itself, or a folder holding it) needs "All". A run that can change an add-on does not start with nothing selected, and a check after an update needs a selection. **Look only** and the runs that only report (Explain, Find what went wrong, Combine or split, Find gaps) build nothing: the plan, the first files and the checks are refused there. A new thread starts on New add-on.
- **The reader has no tools:** the second read at Thorough runs as a helper whose every tool call is refused.
- **A Mission asks only in its first minute.** After that, the question tool is refused and the model notes the question with its recommendation on the list for the end (`creator_note`).
- **The yes to a build** is the user's own newest message, written after the plan ("yes", "build it", "go ahead"; a "no" or "wait" in its first words is not a yes; a yes said before the plan does not count).
- **The way back:** each button acts only where it makes sense (Apply once; Undo only what was applied), Undo puts back the backup taken by that card's own Apply, and a backup is exact (its tests too, links kept as links), one folder each. Remove keeps the removed add-on's folder as a backup. A hand-off never overwrites an earlier one. Every write Creator Plus itself makes in the build folder (the plan's brief, the first files, the passport, the hand-off) goes through one helper (`lib/safewrite.js`): no link anywhere on the way from the thread's folder (each part checked), new files made with O_EXCL|O_NOFOLLOW, replacements by a new file and a rename.
- **Logs:** helpers' threads are not read (whether a helper of a sealed thread is sealed may not be known after a restart).
- **Switched off,** the page shows the switch alone and the server gives nothing else.

## The four checks

`creator_check`: the add-on loads (every file parses; its index.js imports with the app's Node); its tests pass; the fit check is clear (the plan and the add-on's own code); the trial install works (copied into a throwaway app-data folder inside Creator Plus's own folder, `trial/`, with a setup made from the app's web template, registered there with the app's own `dsh plugin add` and composed with `--dump-config`; nothing is started on a port). Every command is a fixed one, run with `execFile`, the trial folder as the app-data folder, inside the sandbox.

## Not built, not verified

- **A real model's scorecard of the eight self-tests.** The code parts run on the page (5 pass by themselves; Rebuild, Look and the rest of Improve need a model: their prompts are in `creator_selftest`).
- **Reading a Recon thread's text** after your yes, by a reader with no tools: not wired. Recon threads are read as structure only (which tool failed, and the kind of error from a fixed list).
- **An installed add-on's tests:** an installed copy carries none. Set the Plus folder to run them after an update and with a change.
- **Apply in the real app** (the plugin manager installing a new add-on, a change copied into an installed add-on) was tested with stand-ins only. A Plus update replaces a changed add-on; the installer keeps your changed files aside.

## For Tuner Plus

Each finished build (all four checks passed) leaves a record in `<app data>/creator-plus/builds/<time>-<folder>.json`, masked: the brief, the plan, a summary, the checks (`loads`, `tests`, `fit`, `trial`), the model that built it, and the fixes (the error of the last failed check and the change that made the checks pass).

## Tests

`test/parts.test.mjs`, `test/plugin.test.mjs` and `test/client.test.mjs`, with stand-ins only (no real app, no real app data). One test runs the real macOS sandbox with a stand-in home folder in a temporary folder and checks that a program inside cannot read or write outside its places, start launchd's tools or `open`, signal other processes, reach the network or see a key. Run them with the app's Node: `ELECTRON_RUN_AS_NODE=1 "/Applications/DeepSeek Harness.app/Contents/MacOS/DeepSeek Harness" --test test/*.test.mjs`.

## Missions in Creator Plus (Mission stage E, 20 November 2026)

Creator Plus's rules hold for it: its checks run in Mission's strictest fence without the internet and without keys (`longRunRules` → `{offlineChecks, cleanEnv}`), its helpers run no commands, the fixed blocks of the fit check stay, and nothing reaches your real setup without your yes.

- **Your yes for the real setup.** A ready add-on (`creator_check`) or a prepared change (`creator_change`) is a card on Settings → Creator Plus, as before. When a Mission's helper made it, it also waits in the Mission's card above the chat box (`mission.askYes`, addon `creatorPlus`, an act that never holds a helper up): "Install … in your real setup" or "Apply the change to … in your real setup", with Creator Plus's own question. Its (i) in the Mission's card says to read the code on the page first (Show the code). Apply and Undo on the page are unchanged.

## Starts on the Creator preset; no PTC (item 7, 21 November 2026)

New Creator Plus threads start on the app's **Creator** preset (id `cordis`) by themselves: Settings → Spaces → Workshop → Preset in this space is "Creator only" by default. The left panel starts the thread with `agentPreset: 'cordis'`, Modes greys the app's preset menu in this space (with an (i) saying why) and switches a blank Creator Plus thread back to Creator if another preset is picked elsewhere. The Creator preset is the only one that brings the two inspection tools, `cordis_inspect_list` and `cordis_inspect_query`; on Standard or PTC Modes leaves them out quietly. If the Creator preset is not in the app's list (renamed, removed or failing to load), nothing is forced: new threads start on the app's default preset, the menu stays free, and the (i) says that the inspection tools are missing.

**PTC does not work here.** Creator Plus refuses every program (`run_code` included), and under PTC every tool is called from inside a program, so a PTC Creator Plus thread can do nothing. If you set the space's preset to Any and start in PTC anyway, the AI is told to say plainly that Creator Plus does not work in PTC and to start again on the Creator preset (it no longer gets the general "call every tool from inside run_code" note), and the Tools panel's PTC hint is hidden. Setting the space's preset to Standard only keeps it working, without the inspection tools.

## The Workshop space keeps Creator Plus's guard for any mode (Item 4A, stage 6a, 22 November 2026)

Another mode in the Workshop space (a guest), and a thread whose space Modes cannot read, get Creator Plus's fixed rules and the Workshop allow-list: files are written only into creator-plus-builds, no commands or programs, and the guest's own add-on tools outside the list are closed (stricter than Devices). Guests never get the creator_ tools (they need the bar and the method). Mission gets Creator Plus's Mission rules for them, and the bar shows in the Workshop space. With Creator Plus off, guests keep only Modes' own rule. The service says `guestsGuarded: true` and gives `allowed()` (the allow-list) for the Settings line that says what a mode loses in Workshop.

## Schedules for guests in Workshop (Item 4A, stage 6b, 23 November 2026: built and unit-tested only)

- The Creator Plus mode at home keeps its own allow-list, without schedules, as before. A thread whose space could not be read keeps them refused.
