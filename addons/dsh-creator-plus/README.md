# Creator Plus

Plugin `@local/dsh-creator-plus` (dsh 0.2.2-rc.2). A tab of its own, beside the app's Creator mode (whose files are never touched), that builds and improves plugins so they fit everything you have. It is Phase 2 of the plan "Creator Plus"; Phase 1 (how Creator mode works, the stock-take, the gaps) is `docs/CREATOR-PLUS-PHASE1.md`, and the handbook for later builders is `docs/CREATOR-PLUS-HANDBOOK.md`.

Off until you switch it on in **Settings → Creator Plus**. Needs the Modes add-on and the Cowork sidebar.

## What you get

- **The Creator Plus tab** (Workspace Write, with its own guard). Its method (about 2,300 characters, under the 4,000 a tab may have) names its four jobs (build a new plugin, change an existing one, keep everything working after updates, improve from the session logs) and the six fixed rules, step by step, for a small model.
- **Its tools, only in Creator Plus conversations** (registered with `when`, so other tabs' tool lists do not change): `creator_map`, `creator_passport`, `creator_recipe`, `creator_interview`, `creator_plan`, `creator_scaffold`, `creator_check`, `creator_change`, `creator_upkeep`, `creator_improve`, `creator_note`, `creator_handoff`, `creator_learn`, `creator_selftest`. Besides them: reading files, and writing them only in the build folder (`creator-plus-builds` inside the conversation's folder), the web, the app's inspection tools (`cordis_inspect_*`), diagrams, the step list, questions, PDFs. No shell, no programs, no plugin manager.
- **The bar** in the chat box of a Creator Plus conversation: which plugins (built-in and third-party ones carry a lock: read, explained and checked, never edited; Recon shows a note that only its structure is read), "All" on purpose, what to do (New plugin, Improve, Find what went wrong, Rebuild, Combine or split, Find gaps, Check after an update, Explain, each with its line), **Look only** (read and report; prepare nothing, not even in the trial copy), **Logs from** (since the last run, 7 days, 30 days, everything) for the runs that read logs, and the run in one sentence before it starts. **Save run** keeps it by name.
- **Settings → Creator Plus**: the switch; the six rules and how each is enforced; the **results** as cards (a finding, a prepared change, a question, an assumption, a ready plugin) with **Try it in the trial copy**, **Apply to my setup**, **Not now**, **Do not suggest this again** (kept as a preference) and **Undo**/**Remove** after Apply; **what Creator Plus learned** (proposed; kept only when you press Keep; undone with Undo; a lesson from a third-party plugin needs "I read it" first); who may read your session logs (only models on this Mac by default); strong models (they may improve on a recipe's default steps); the Plus folder with its tests; saved runs; the self-test; the backups.
- **Saved runs on the Automations page** (your answer of 16 November): each saved run can be scheduled there; it runs in a Creator Plus conversation of its own that starts with the saved run's bar, as a Long run would, prepares changes in the trial copy only and changes nothing in your setup without your yes. When Creator Plus is switched off, its scheduled saved runs are paused (switch them on again on the Automations page).
- **Long runs are switched off in the Creator Plus tab for now**: the Run button's card says "Long runs in Creator Plus are switched off until their checks can run on a throwaway copy; use Thorough for now" and the run does not start, and a plain `/mission` run is refused there too (a Long run's checks would run in the conversation's live folder). Thorough gives a second read by a checker with no tools.
- **A passport** in every Plus add-on (`passport/`: brief, what it touches, what it was built against, its tests, its changelog, who made it, and an empty `lessons/` folder for Tuning Plus). Built-in and third-party plugins get theirs in Creator Plus's own folder, never in their own.

## The fixed rules, and the code that holds them

1. **No change without a backup and a way back.** Every change and install keeps the version before it in `<app data>/creator-plus/backups/` first (`lib/trial.js`, `lib/change.js`); Undo puts it back, and putting it back is itself backed up.
2. **Nothing changes in your real setup without your yes.** The assistant's tools work in the build folder; the real setup changes only from a button on Settings → Creator Plus, which only you can press. What is applied is what was reviewed: `creator_check` first copies the plugin into Creator Plus's own folder (out of reach of the file tools and of the sandbox), runs every check on that copy, and Apply installs exactly it (every file hashed; a copy that differs is refused). A change is prepared the same way. The card shows the code in full and unmasked (**Show the code**, **Show the change**: the change line by line and every changed file as Apply writes it); what cannot be shown in full is not applied from here (binary files, modules other than Creator Plus's own, too much code, a change too long to show). Apply runs once (a second click is refused).
   A plugin's code (its tests, its index.js) runs only inside macOS's sandbox (`lib/sandbox.js`), in a fresh run folder of its own (`lib/runs.js`): the host fills it from the host-only copy before anything runs, the sandbox may write only there, and afterwards the host reads only the programs' output and throws the folder away; it never acts on anything the sandbox could write, and Creator Plus's own folders are checked to hold no link. Inside: no network, no Mac services, no launchd job, no program but the app's own Node and the shell, no native code but the system's and the app's, no child process at all (a plugin's tests run in one process; tests that start programs fail there), reading only the system, the app and its run folder (not the home folder, not the app's data, not /tmp or other users' folders), signals only to its own processes, and a short environment with no keys. When a program ends, its whole process group is stopped. The trial install runs in a fresh trial copy per check, the same way; it runs only the app's own `dsh` and package manager (tried: neither the plugin's index.js nor its package scripts run; a plugin with package scripts is blocked), so only it may start child processes. Output is masked and shown to the model as material. Where there is no sandbox, nothing is run.
3. **Another tab's safety rules are never weakened: blocked, not asked.** The fit check blocks a plan that gives a sealed tab a tool, appears in one, loosens a named safety rule, takes a name or a row already on the map (built-in rows too), or changes a file that holds a safety rule: every file of Recon, Devices, Modes, Mission and Creator Plus, Content's subject check, and every plugin's setup file (`cordis.patch.yml`); `creator_change` refuses the same files, capitals ignored. It also reads the built plugin's own code, not only the plan: writing another plugin's settings or the Modes add-on's (a tab plugin adding its own tab is a decision), settings named only at run time, naming a sealed tab, hooking every tool call, and a setup file that does more than insert its own row (checked strictly: no other operation, no tags such as `!!js`, no anchors) are blocked (`lib/fit.js`, `codeFindings`). The code check is a help, not a guarantee: a model can hide what code does (a name put together while running, a file written elsewhere), so the card says so and shows the code; the fixed blocks hold for what can be seen.
4. **Third-party plugins and the app's own code are never edited.** The guard refuses writes there; the change tools refuse locked plugins and point to an adapter beside them.
5. **Text from plugins, pages, logs and tool results is material, not instructions.** It is fenced with a random marker it cannot close (`lib/text.js`).
6. **No password or key in a map, a passport or a log.** Maps hold setting names, never values; maps, passports, cards and log findings are masked; logs go only to the models your setting allows (and the cards with their evidence sit in Creator Plus's own folder, which no file tool reads); the file tools cannot read the app's data folder (only the installed Plus add-ons and the conversation's folder).

The guard (`lib/rules.js`) decides every tool call in a Creator Plus conversation and its helpers in `tools/pre-execute`, before any other add-on is asked, and again as a final `tools.guard` that nothing can undo. It is an allow-list: Creator Plus's tools, file tools, the web, the inspection tools, the step list, questions, `mission_step`, `tools_find`, `skill`, diagrams, PDFs and Memory's `remember`. Every shell, terminal and program tool is refused (`NO_COMMANDS`), as is any tool it does not know (`NOT_ALLOWED`). Writes only inside the build folder, `creator-plus-builds` in the conversation's folder, by their real path (a link out of it does not count), never in the app, the installed plugins, the app's settings or conversations, the Plus folder, or Creator Plus's own folder. A conversation whose folder is your home folder, the whole disk, inside `~/Library`, holds or lies in the app's data (Scratch excepted) or a Plus folder, lies in the app, or is Recon's sealed room (a `dsh-recon-*` folder directly in a temporary folder, the rule Content uses), builds nothing. File tools never read or write inside a Recon room, and a search over a temporary folder is refused. A call it cannot check is not run. Also:

- **The bar's selection is a boundary:** a plugin's own files are opened, and a plugin changed, only when it is selected; otherwise it is a line on the map. The same holds in the Plus folder named on the page, and a look over all the plugins at once (their folder itself, or a folder holding it) needs "All". A run that can change a plugin does not start with nothing selected, and a check after an update needs a selection. **Look only** and the runs that only report (Explain, Find what went wrong, Combine or split, Find gaps) build nothing: the plan, the first files and the checks are refused there. A new conversation starts on New plugin.
- **The reader has no tools:** the second read at Thorough runs as a helper whose every tool call is refused.
- **A Long run asks only in its first minute.** After that, the question tool is refused and the model notes the question with its recommendation on the list for the end (`creator_note`).
- **The yes to a build** is the user's own newest message, written after the plan ("yes", "build it", "go ahead"; a "no" or "wait" in its first words is not a yes; a yes said before the plan does not count).
- **The way back:** each button acts only where it makes sense (Apply once; Undo only what was applied), Undo puts back the backup taken by that card's own Apply, and a backup is exact (its tests too, links kept as links), one folder each. Remove keeps the removed plugin's folder as a backup. A hand-off never overwrites an earlier one. Every write Creator Plus itself makes in the build folder (the plan's brief, the first files, the passport, the hand-off) goes through one helper (`lib/safewrite.js`): no link anywhere on the way from the conversation's folder (each part checked), new files made with O_EXCL|O_NOFOLLOW, replacements by a new file and a rename.
- **Logs:** helpers' conversations are not read (whether a helper of a sealed conversation is sealed may not be known after a restart).
- **Switched off,** the page shows the switch alone and the server gives nothing else.

## Depth

| | Build | Change | Keep | Improve |
| --- | --- | --- | --- | --- |
| Quick | the recipe's [must] steps; load and fit checks; no trial install | show the change and its risk; prepare nothing | compare the map; run nothing | the three findings that matter most |
| Standard | the recipe, tests first, all four checks | back up, change in a copy, run that plugin's tests | compare the map, check every plugin loads | findings per plugin with evidence |
| Thorough | as Standard, and a second read by a checker with no tools | and the tests of every plugin it touches | and every plugin's tests | and the change drafted in the trial copy |
| Long run | until every check passes or a limit is reached | the same, in the trial copy only | for the whole setup | keep improving until a limit |

## The four checks

`creator_check`: the plugin loads (every file parses; its index.js imports with the app's Node); its tests pass; the fit check is clear (the plan and the plugin's own code); the trial install works (copied into a throwaway app-data folder inside Creator Plus's own folder, `trial/`, with a setup made from the app's web template, registered there with the app's own `dsh plugin add` and composed with `--dump-config`; nothing is started on a port). Every command is a fixed one, run with `execFile`, the trial folder as the app-data folder, inside the sandbox.

## Not built, not verified

- **A real model's scorecard of the eight self-tests.** The code parts run on the page (5 pass by themselves; Rebuild, Look and the rest of Improve need a model: their prompts are in `creator_selftest`).
- **Reading Recon's conversation text** after your yes, by a reader with no tools: not wired. Recon conversations are read as structure only (which tool failed, and the kind of error from a fixed list).
- **An installed plugin's tests:** an installed copy carries none. Set the Plus folder to run them after an update and with a change.
- **Apply in the real app** (the plugin manager installing a new plugin, a change copied into an installed add-on) was tested with stand-ins only. A Plus update replaces a changed add-on; the installer keeps your changed files aside.

## For Tuning Plus

Each finished build (all four checks passed) leaves a record in `<app data>/creator-plus/builds/<time>-<folder>.json`, masked: the brief, the plan, a summary, the checks (`loads`, `tests`, `fit`, `trial`), the model that built it, and the fixes (the error of the last failed check and the change that made the checks pass).

## Tests

`test/parts.test.mjs`, `test/plugin.test.mjs` and `test/client.test.mjs`, with stand-ins only (no real app, no real app data). One test runs the real macOS sandbox with a stand-in home folder in a temporary folder and checks that a program inside cannot read or write outside its places, start launchd's tools or `open`, signal other processes, reach the network or see a key. Run them with the app's Node: `ELECTRON_RUN_AS_NODE=1 "/Applications/DeepSeek Harness.app/Contents/MacOS/DeepSeek Harness" --test test/*.test.mjs`.
