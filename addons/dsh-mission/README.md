# Mission

Add-on `@local/dsh-mission` (dsh 0.2.2-rc.2). What it does:

- **Mission access and checkpoints** (since 0.36.0): three access levels that keep the assistant inside a thread's folder, and checkpoints of that folder that the user can go back to.
- **The run** (since 0.37.0): `/mission <goal>` hands the goal to several models in fixed roles, with real commands as the proof. It is described under "The run" below.
- **One Mission** (since stage B, 19 November 2026): the run and the former Long run are one thing, called **Mission**, started with **Start Mission** beside Send or a typed `/mission <goal>`, with one status strip and one main button. See "Mission and Long run become one" below. Choosing **Mission** in Depth only selects it (since stage D, 20 November 2026).
- **Helpers at once** (since stage D, 20 November 2026): several helpers work on checklist items at the same time, a helper that needs your answer or your yes waits in the card while the others carry on, and two helpers never change the same file at once. See "Helpers at once, parking, one writer per file" below.

Nothing happens until the user starts a Mission or types `/mission` in a thread.

## Mission access

| Level | Inside the thread's folder | Outside it |
|---|---|---|
| **Restricted** (`/mission restricted`) | New files are free. Changing or deleting an existing file is asked once per file. | Nothing is read or changed, and the user is never asked. |
| **Ask** (`/mission ask`) | As Restricted. | Reading is asked once per place. A change is asked for by the app's own sandbox. |
| **Auto** (`/mission auto`) | Free: no asking. | As Ask. |

`/mission on` switches on the access level chosen in Settings → Mission (default Restricted). `/mission off` switches Mission access off. `/mission` alone shows what is on (and how a run stands) and lists the commands.

A file the assistant created itself in the thread is its own: changing it later is not asked.

## How Mission access holds

1. **Every tool call is decided before it runs** (`tools/pre-execute`; rules in `lib/guard.js`, a pure function). Paths are taken from the call's arguments (`file_path`, `path`, `files` and the like) and compared in their real spelling, so a link that points out of the folder counts as outside. A question goes to the user through the app's own approval card (`approval.request`); the answer is remembered per file (inside) or per place (outside) in `<home>/mission/conversations.json`.
2. **The app's sandbox does the fencing for changes.** Switching Mission access on puts the thread on the app's **Workspace Write** preset (sandbox `workspace-write`, approval `ask`). The app then refuses any write outside the folder at the operating-system level, for file tools and for terminal commands alike. To change something outside, the assistant has to retry the call with `sandbox_permissions`, and the app asks the user. In Restricted, Mission refuses such a retry before it gets that far.
3. **Terminal commands** cannot be asked about file by file, so they are checked afterwards. A checkpoint is taken before every command. After it, in Restricted and Ask, any file that existed before, was changed or deleted by the command, and is not approved, is put back from that checkpoint. The command's output is kept and a note is added telling the assistant what was put back and how to ask (`mission_request_files`, or the edit tool). New files and everything the project ignores are left alone.
4. **Reading outside from a command** is checked from the command's text only: words that are paths under the user's home (or `..` leading out of the folder) and are not system places (`/usr`, `/bin`, `/opt`, `/tmp` and so on). Restricted refuses the command; the other two ask.
5. **Helper agents** (sub-agents) of a guarded thread are under the same Mission access and share its approvals. A helper's question is put to the user through the thread it works for.
6. **The assistant is told the rules** (prompt section `mission:rules`), including that in Restricted it must not ask.

The tool `mission_request_files { files, why }` asks the user once for several existing files, for example before a formatter runs.

## Checkpoints

- Kept with git in a store of their own: `<folder>/.dsh-mission/checkpoints.git` (`GIT_DIR` there, `GIT_WORK_TREE` the folder). The project's own repository is never read or written, except that `/.dsh-mission/` is added once to its local, uncommitted ignore list (`.git/info/exclude`) so the store does not show up in `git status`.
- Taken when Mission access is switched on, at the start of every turn, before every terminal command, and by `/mission checkpoint [name]`. When nothing changed since the last one, no new one is made.
- `/mission checkpoints` lists them, newest first, numbered. `/mission back 12` puts the whole folder back as it was at checkpoint 12. The state just before going back is kept as a checkpoint too, so going back can be undone, and the list never loses an entry.
- **Not kept:** what the project ignores in `.gitignore`, and always `node_modules/`, `.venv/`, `venv/`, `__pycache__/`, `.DS_Store`. Such files are neither protected from commands nor put back.
- Needs `git` (`/usr/bin/git`, or Homebrew's). Without it Mission access still decides tool calls, but there are no checkpoints and a command's changes cannot be put back; the command says so when Mission access is switched on.
- **No undo available** (no git, a folder judged too broad, a folder too big to copy). Not left silent any more (review of Phases 1-3, item 6): the model's rules for that thread say "no undo is available in this folder" (not "put back at once") and ask it to tell the user once; the first command's result carries the same words once per thread (also in a thread that had Mission access on before a restart); in Restricted, a command that could change files (anything not plainly a reader: `mayChangeFiles` in `lib/guard.js`) is asked about on the app's approval card, once per exact command, because nothing can put its changes back; Ask and Auto are told, not asked (Ask asks about files and places, not commands). Chosen so a Long run stays usable: readers (ls, cat, grep, git status/log/diff...) run freely, and a helper's question times out and sets the item aside as before. A run's start text says "No checkpoints are kept of this folder" instead of "/mission back 0".
- **Too broad** now also means Pictures, Music, Movies, iCloud Drive, Google Drive, Dropbox, OneDrive (and the drives' top folders under `Library/CloudStorage`) and an external disk's top folder (`/Volumes/<name>`). A project inside any of them is fine. **Old checkpoints** in a folder that is judged too broad now stay reachable read-only: `/mission checkpoints` lists them and `/mission back <n>` puts the files of that checkpoint back, but no new checkpoint is taken (that would copy the folder), so that restore cannot itself be undone and files made after the checkpoint are left alone.
- A folder refused as too big removes the store it made for counting (also when a `.dsh-mission` folder already existed), and a store that holds no checkpoint yet is counted again, so a restart never skips the size check.

The app shows a command's answer as one line that opens with a click; each answer therefore starts with the essential line.

## Limits

- A script can read a file elsewhere on the Mac without naming it in the command line. It cannot change one: the sandbox stops that.
- A change outside the folder is asked for by the app per call, not once per place.
- The app's approval button reads "Allow once"; for a file inside the folder, Mission remembers the yes for the rest of the thread all the same.
- A command that runs in the background and changes files after it has returned is not caught by the check after the command; the files are still in the earlier checkpoint. (A Mission with several helpers refuses such commands, or holds the folder until a command the app moved to the background ends: stage D, review fixes.)
- A nested git repository inside the folder is recorded as a link, not copied.
- Changes the user makes by hand are never undone by the put-back, but `/mission back` returns the whole folder, the user's own later changes included (they are in the "before going back" checkpoint).
- Very large files that the project does not ignore are copied into the store at every change.

## Where Mission does not work (0.57.0)

The rules are in `lib/gate.js`, a pure function.

- **Sealed threads (Recon).** (Since 16 November a Recon thread may run a Mission where Recon's settings allow it, started with Start Mission; since stage E also with a typed `/mission <goal>`. See "Recon" below and Stage E. The rest of this bullet holds where Recon's settings keep Missions out.) Other add-ons leave a sealed thread alone, and so does Mission. When the Modes add-on says a thread is isolated (`modes.isolated(id)`; a Modes add-on that cannot answer counts as isolated), `/mission` answers "Mission is not available here: this is a sealed thread (Recon), and other add-ons leave it alone." and changes nothing: no permission preset, no checkpoint of the folder, no run. `mission_step` answers the same. Only `/mission off`, `stop` and `end` still work, so Mission access or a run an earlier version started there can be taken back. Mission access left on from before is not applied any more (no checks of tool calls, no checkpoints at the start of a turn). A run left on there (one an earlier version started, or one in a thread moved to Recon) cannot move, because Modes refuses `mission_step` in a sealed thread; so it is paused a moment after the next turn the app starts there, with the reason kept in the run, and does not use up the goal's rounds. `/mission end` closes it with a report.
- **A tier with Sub-agents off.** A run's planner, workers and reviewer are sub-agents. When the thread's tier has Sub-agents switched off (Model tiers: `modelTiers.resolveTier(id).subagents === false`), `/mission <goal>` and `/mission resume` are refused with the reason and what to do (switch Sub-agents on for the tier in Settings → Model tiers, or give the thread another tier). Nothing is switched on first. A run already under way is paused at its next step (`mission_step` pauses the app's goal and keeps the reason, which `/mission` shows), so it does not use up rounds; `/mission resume` carries on once the tier allows sub-agents again. Mission access and checkpoints (`/mission restricted`, `ask`, `auto`, `checkpoints`, `back`) start no helpers and still work.
- **How the owner's decision is read.** The decision says to refuse `/mission` where the tier allows no sub-agents. Mission refuses there what needs helper models: starting a run and carrying one on. The Mission access levels still switch on such a tier (`/mission restricted`, `ask`, `auto`, `on`, which also set the app's permission preset and take a checkpoint), and checkpoints still work, because none of them starts a helper. In a sealed thread everything but taking back is refused, as above.
- `mission_step` is not registered with Model tiers' own sub-agent gate (`registerSubagentTool`): that gate also counts the step's own running helper, so on a tier capped at one sub-agent the conductor's next call (which only waits for that helper) would be refused and the run would stall. Mission reads the tier's switch itself instead.

## Settings

Settings → Mission: the switch (`enabled`, default on), the access level `/mission on` uses (`defaultMode`, default `restricted`), the models for a run (`roles`, `projects`), the checklist limits of every Mission (`maxItems` 12, `maxTries` 3) and the starting values of each thread's Mission settings (`longMinutes` 120, 0 = no time limit; `longLaps` 10, 0 = no lap limit; `longHelpers` 4, Helpers at once, 1 to 8, since stage D; `longNeeds` When it needs you, `ask` unless changed; `longWaitAsk` and `longWaitHold`, Wait for me for Ask, keep working (30 minutes) and for Ask and wait (until I answer), see "When it needs you" below; and the other `long*` keys). `waitMinutes` (3) is off the page since then: it is the starting value of Wait for me (Ask, keep working) when that was never set (3 becomes 30), the approval wait of runs from before stage B, and Tool access's wait for a thread's own request during a Mission. `maxReviews` and `maxSteps` are no longer on the page (since stage B); their keys stay so older settings files load, and runs saved before keep their limits in their own `run.json`.

## The run (since 0.37.0)

`/mission make every test pass and add a --json option` starts a run with the thread's Mission access (or the Settings default). An access level named first applies to it: `/mission auto …`.

### What happens

The order of work is fixed and the add-on drives it (`lib/run.js`, a pure state machine). A model never decides that something passed.

| Step | Who | What |
|---|---|---|
| **Plan** | planner | Reads the folder and answers with a checklist: each item has a "done when" and, where possible, **a shell command that exits 0 only when it is done**. Also the overall commands (tests, build) that must pass at the end. A plan that cannot be read becomes one item, the goal itself. |
| **Work** | worker | One item at a time until stage D; since then up to Helpers at once items at the same time, and two helpers never change the same file at once (see the stage D section). After the worker, the item's command is **run by the add-on** (`lib/shell.js`, in macOS's sandbox: it may write only in the folder and in temp). Pass: the item is PASSED. Fail: the item is tried again with what the command said. The last try goes to the planner's model ("senior worker"). After all tries: NOT FINISHED. |
| **Checks** | the add-on | Runs the overall commands. One that fails becomes a new item. |
| **Review** | reviewer | Gets the goal, the checklist, the command results and what changed since the start (from the checkpoint store). It judges the items no command could prove (they become REVIEWED) and may send items back or add up to four. It cannot overrule a failing command. |
| **Finish** | the add-on | The report: every item with its mark, the overall commands, what waits for the user, and the checkpoint to go back to. "Complete" only when every item is PASSED or REVIEWED and the overall commands pass. |

### How it keeps going

The app's own goal system is the clock. Starting a run creates an app goal (`goals.create`); the app's round driver then gives the thread one turn after another. In each round the thread's own model (the "conductor") calls the one tool `mission_step`, which does the next step and returns what happened; the conductor says it in a sentence. While a run is on, every other tool call by the conductor is refused, so a weak model cannot wander off and start doing the work itself. The helpers are ordinary sub-agents of the thread and are under the thread's Mission access.

- `/mission stop` pauses (the app's Stop button does the same), `/mission resume` carries on, `/mission end` closes the run with a report, `/mission report` shows how it stands.
- The run is on disk after every step, so it survives an app restart: `/mission resume`.
- A step that fails three times running closes the run with a report.

### PTC preset, long steps and stalled runs (0.37.1)

- **PTC.** In the app's PTC preset a thread can call only `run_code` directly and reaches every other tool from inside that program. 0.37.0 refused `run_code` to the conductor ("call mission_step and nothing else"), so a run in PTC could never step: the owner's first run used all 70 rounds on that. Now the program is let through and what it calls is decided one by one, so only `tools.mission_step({})` gets through. The conductor's note gives the exact program in PTC threads.
- **Long steps.** A step now runs on its own, apart from the tool call that started it. A call of `mission_step` only waits for it: 100 seconds in PTC (the app stops a program after two minutes unless the model asks for more, ten minutes at most), 70 minutes otherwise. When the wait ends first, the tool says the step is still under way and to call again; the next call finds the same step. A call that is cut off does not stop the step, unless the goal was paused (the user pressed Stop), in which case the step stops too.
- **The app's round cap** for the goal is set far above a run's own step limit (3000), because waiting rounds use rounds. A run's own limits are what end it.
- **Stalled runs.** Five rounds in a row without a call of `mission_step` pause the run, with the reason shown by `/mission`. Before, such a run used every round it had. Since 0.57.0 the count, and the pause, are made a moment after the turn starts: inside the app's turn-start event a goal cannot be paused (the app refuses to write to the thread while it is handing out that event), so until then this brake did not work in the app, only in the tests. A pause that the app refuses is not reported as made.

### When the user is away

Since stage D (20 November 2026), for a Mission (kind `long`): a helper that needs your yes no longer waits 3 minutes with a card over the chat box. Its request is parked in the Mission's card above the chat box, its work so far is kept, and another helper takes its place; nothing times out (see "Approvals parked" below). What follows is how it worked before, and still works for runs of the old kind `mission`.

In Restricted and Ask a worker may need the user's yes for a file. The question appears as a card **in the main thread** (the app answers a helper's own request with a no and no card, so the question is put through the thread the helper works for). If no answer comes within `waitMinutes` (default 3), the item is marked NEEDS YOU and the run carries on with the rest. `/mission resume` after the run takes those items up again (since the stage C review: it asks how much more time to give, `/mission resume <minutes>`, and not after End).

### Which model does what

**Since 0.40.0 the default is one model for everything:** every role runs on the thread's own model, so nothing else has to be loaded. The roles' own models apply only when the thread is set to "Different models" with the models chip in the chat box (the Modes add-on keeps that choice and answers `modes.helperModels(sessionId)`; without the Modes add-on it is one model). The first line of a run's start says which it is ("one model" or "3 models") and names them.

With "Different models", for each role (planner, workers, reviewer), in this order: the project's own choice, Mission's choice, the Model tiers role model of the thread's tier (`plan`, `implement`, `review`), the thread's model. Settings → Mission has the pickers: "Models for a run" for every project, and "Per project" for one folder. They are stored as JSON in the settings `roles` and `projects` (keyed by the project's folder).

### What a run leaves behind

In `<folder>/.dsh-mission/runs/<id>/`: `run.json` (the run as it stands), `log.jsonl` (one line per step: kind, role, model, milliseconds, item, try, the command and whether it passed), `steps/` (every helper's answer in full) and `report.md`. `<home>/mission/runs.jsonl` gets one line per finished run with the path of its log. Nothing reads these yet: they are there for a later review by the self-improvement add-on.

### Limits of the run

- Its quality is the quality of the plan. A check command that proves little lets weak work pass; the reviewer is the only guard for that.
- "REVIEWED" is a model's judgement, not a proof. The report says which is which.
- One item at a time, no workers in parallel: true until stage D. Since then up to Helpers at once items (4 unless changed) are worked on at the same time; see the stage D section. Runs of the old kind `mission` still work one item at a time.
- No browser checks of its own. A worker can use whatever browser tool or command the thread has, and a check command can be a browser script, but the add-on does not drive a browser.
- The conductor has to call `mission_step` and should relay the final report. A model that does neither stalls the run or leaves the report in the tool result; `/mission report` shows it either way.
- Proof commands run with the user's shell PATH and without network limits, like the assistant's own terminal.

## Long run (overnight 16 November 2026)

This section is the history of the feature that is now simply called **Mission** (see "Mission and Long run become one" below). What it says still holds unless that section changes it: the Long run button is now Start Mission, Resume is on the main button, the card is the status strip, and typed `/mission <goal>` runs work the same way.

A long run is a Mission run of its own kind; `/mission` runs keep every rule they had.

- **Start** with the **Long run** button next to Send (called Run before 1.0; the owner's choice of 16 November 2026): type what the run should do in the chat box and press it. A question first says in plain words that the assistant will then work alone, in up to 10 laps, for up to 120 minutes by default, and may use many tokens; nothing starts until you confirm. In a thread that is not open yet the button still works: your message is sent first, then the run starts from the same words. That waiting goal belongs to the chat box where the button was pressed and then to the thread that box turned into: no other chat box or Split pane takes it, it is dropped (with the reason on the button) when the start fails or that thread is left or after three minutes, it waits while the thread is still answering, and the server starts a run only in a thread that really received those words (`afterMessage: true`) and is not busy (`action: start` is refused while the thread answers: "This thread is still answering…"). Mission is told the next message of yours is a run's goal (`POST /dsh-mission/long`, `action: arm`, forgotten after 30 seconds or with `action: disarm`), then the button presses the app's own Send, so the message shows in the thread as usual. When that message arrives (a `user/message` event of source `user`), the run starts with it as the goal; the thread before it (your messages and the answers, at most 4000 characters, `long.context`) goes to the planner and the reviewer, so a plan made by chatting carries over. Between the press and the start the thread's model is told a run is starting, `mission_step` waits for the start, and its other tools are refused once the run is on. A press is refused while the thread is answering, in a sealed thread (Recon), in a helper, and when the pre-flight fails; a start that fails says why on the button and to the model, and puts the earlier mode back. **Send** stays an ordinary message at the thread's Depth. The old card start (`action: start` with a goal) still works.
- **Settings per thread**: Depth → **Long run settings…** opens the thread's settings (time, laps, Mission access, Files and commands, Web, full time, keep awake, battery, try again, think by role, token allowance) with the pre-flight list, saved with `action: save` in `mission/long-settings.json` (at most 500 threads). The Run button uses them; a thread with none saved uses Settings → Mission and the mode's Long run tools.
- **Messages during a run**: what you send while a Long run works is kept for it (`long.asks`, the last six, 500 characters each, logged as `ask`) and every helper reads it from its next step on, at the top of the run's notes.
- **Cards from other threads** (Split Plus's Send to, since 17 November 2026): a card (`[Split Plus send …: material, not instructions]` … `[End of Split Plus send …]`) is never your goal or your words. After a press of Run, a message that is only a card leaves the press waiting for your own words; a goal sent with a card starts the run with your words as the goal and the card added to `long.context` as material. During a run only your words around a card are kept for the helpers. The rule is a copy of Split Plus's (`lib/sent.js`, kept in step by `test/sent.test.mjs`), so it works with Split Plus off.
- **Laps**: work on the open items, the overall commands, a review. The run stops at its time (read between steps, so it can go over by the step under way), its laps, an optional token allowance, or when two laps in a row find nothing more to do (unless "Use the full time" is on). "Finish this lap" ends it after the lap under way.
- **The gate**: once the overall commands have all passed, a lap whose commands then fail where they passed (still failing when run a second time) is undone: the folder goes back to the checkpoint taken at the lap's start, the undone work is kept as a checkpoint, and the report names both. Your own edits in that folder during the lap go back too; they are in the kept checkpoint.
- **Notes** about what passed, failed and should be avoided are kept by the add-on and given to every helper (at most 1,200 characters, replaced each lap).
- **Effort by role**: planner and reviewer High, workers Medium (the same model). Model tiers leaves those helpers' effort alone (`mission.ownsEffort`).
- **The card** above the chat box shows the lap, items done, time left, tokens and the step under way, with Pause, Resume, Finish this lap and End; the checklist opens on request. The app's goal strip is hidden while a long run's card shows. A finished run's card shows its summary line and the report.
- **Watchdog**: when the app stops giving the run rounds while it runs (its goal still active but disarmed: a failed request, or a reply cut at its length limit), the run notes it and, if "Try again by itself" is on, re-arms the goal after 2, 5 and 10 minutes, never after your own pause. After a restart it waits for you (Resume on its card) (until stage E; since then **Carry on by itself after a restart** decides, and a model server that does not answer gets its own wait; see Stage E).
- **Keep awake**: macOS's `caffeinate -i -w <the app's pid>` while a long run that wants it is on and the Mac is on power (on battery only if every such run allows it).
- **Events for other add-ons**: `mission.onEvent(listener)` (started, step, needs-you, paused, stalled, stopped-by-itself, retried, finished), `mission.isRunning(id)`, `mission.view(id)`. Alerts send run alerts from them; Alerts and Notify keep a running run's rounds quiet.
- **Every mode but Recon, in place** (the owner's choice, 16 November 2026: a run never moves a thread to another mode). While a Long run is on, its thread and helpers get the tools it needs on top of the mode's own: the card's **Files and commands** (every tool, as in Cowork) and **Web** switches, whose starting choice per mode is on Settings → Modes → Long run tools. The mode keeps its own way of working (its instructions); the model is told the run's tools override what the mode says about tools. Modes asks Mission (`mission.longRun(id)`) and puts the tools on right before the first round (`modes.refreshTools`) and again when the run ends.
- **Read Only modes** (Data, Research, Chat, Automations: Modes' `readOnly`) only warn: "This mode is Read Only, but a Long run can change files in this thread's folder." The run selects the Workspace Write preset; when it ends, the earlier preset and access level come back (`long.restore`, a `sandbox/mode` event), and the Mission access goes off again if the run switched it on. `/mission` access levels and ordinary runs are still refused there (since stage E a typed `/mission <goal>` works there too; the access levels stay refused; see Stage E); `/mission status`, `report`, `pause`, `resume` and `end` work on a Long run there.
- **Defaults** are on Settings → Mission, "Long runs".

## Engine fixes (item 1, stage A, 19 November 2026)

Why the owner's Long runs did not finish (`REVIEW-REQUIREMENTS-1.md`, sections 1.2 to 1.6), fixed in the engine. The run card and its buttons look as before; Long run and Mission keep their names for now. Every fix has a test in `test/engine.test.mjs` that fails on the code before it.

- **An empty helper answer is a failure.** The app's helper result has no request or tool count, so Mission counts them itself from the helper's session events (`step/start`, `tool/call`, its own and those of helpers it starts). No text, no tool run and (where the events cannot be seen) no file changed is a failure: it goes through the retry without a thinking level, counts toward the three-in-a-row pause, does **not** use up the item's try, and its step file holds the reason, never 0 bytes. A helper with no request at all is said plainly: "The app stopped the helper before it reached the model (a route or setting problem)." The `work` log line has `stopReason` and `effort`.
- **Thinking level.** Before a helper is sent a level, Mission asks the app for the model's listed levels (`llm.resolveModelInfo`, as Model tiers does) and the thread's tier (`modelTiers.resolveTier().effort`). None is sent when the model lists none or the tier says off; otherwise the asked level or the nearest listed one (`lib/effort.js`, a copy of Model tiers' preferences; on a tie the lower). Not known (no model information): asked for as before. The retry without a level stays as the safety net.
- **Status line.** Workers start their report with `DONE:`, `PARTLY:`, `BLOCKED:` or `QUESTION: … | ASSUMING: …` (`statusOf` in `lib/prompts.js`). `BLOCKED: no / none / n/a / not needed` counts as done. The old "starts with BLOCKED" reading is used only when there is no status, and no longer fails on "BLOCKED: none". A QUESTION is kept in `run.questions` (`{id, text, assume, items, status: 'open', askedAt}`), the item is finished on the default and noted "Assumed: …", never failed. The report lists open questions with the default used.
- **Three step errors in a row pause** the run (plain reason; the raw error is kept in `run.stalledDetails` and the log), instead of ending it. Only End, the time or the other limits end a run.
- **A paused run takes no step.** `mission_step` and `runner.step` answer "The run is paused; it carries on when the user presses Resume." and start no helper.
- **Paused time does not count.** Every pause (yours, a problem, the idle brake, a self-stop, a restart) sets `run.pausedAt`; Resume (and the watchdog's retry) adds the paused span to `long.deadline` and `long.pausedMs`. The report says how long it was paused.
- **The clock.** (a) No new step when less time is left than the run's median step time (once three steps are measured): the report instead ("too little time was left for another step"). (b) Every 30 seconds a wall clock ends a Long run whose deadline plus grace (10% of its time, at most 10 minutes) has passed while no step moves, with "its time was up" and the normal report (keep-awake lets go with the `finished` event). A paused run is never ended this way. (c) A step still running past deadline plus grace is stopped; its item keeps its try and the report says the last step was cut short by the time limit. A run ended while its thread is closed has its goal closed when the thread opens (`goalClosePending`).

- **Checks.** A check (or an overall check) whose last pipeline ends in `wc`, `sort`, `head`, `echo` or `cat` always passes, so it counts as no check (the reviewer judges; `$( … )` is left out, so `test $(… | wc -l) -ge 1` stays). (`mission.budgetStopped`, called by Budget guard). ## Review fixes (19 November 2026)

What the review of the engine fixes found, and what changed. Nothing else in how Mission works was changed.

- **"BLOCKED: no …" was read as done.** Only the word on its own (`BLOCKED: none`, `BLOCKED: n/a.`) or followed by a clause that says the work is done (`BLOCKED: none, item 3 is done`) counts as done now. `BLOCKED: no write permission for config.json`, `BLOCKED: None of the tests can run without a database` and `BLOCKED: no, but the build fails` are blocks again, as before the engine fixes.

- **"Its folder is gone" only when it surely is:** the file is missing (`ENOENT`), the run's own folder is missing, the folder above the project is there (on `/Volumes/<disk>`: the disk is mounted), and the thread is not in the Cowork trash. ## Helper failures in a Long run (lab run, 19 November 2026)

- **A reviewer with no usable answer** (empty, unreadable after the format ask, or failed) is a helper failure, not a lap that found nothing. The lap does not end, no review is used up, and the review is taken again in the next step (an empty answer is first tried once more without a thinking level, as before). It counts toward the same three-in-a-row pause as a failing worker; the pause says "3 helpers in a row failed. The last one: The reviewer gave no usable answer: …" (one neutral sentence for workers and reviewers alike, since they share the count; the last reason names which). Only a JSON object with a `verdict` counts as a review: a snippet the reviewer quoted (`{"name": "app"}` from a package file) is skipped, a real verdict after it is still read, and prose with no verdict goes through the format ask and, failing that, is unusable. The "taken again" notice is kept apart from the reviewer's note (`reviewRetry`), so the report keeps the last usable note and never says the review "will be taken again" after the run ended. Two such reviews can no longer end a run with "two laps in a row found nothing more to do". The log line gets `unusable: true`. A /mission run (not Long) is unchanged.
- **A plan that cannot be read** still becomes one item, the whole goal. The plan step, its log line (`note`) and the report now say "The planner gave no usable plan, so the whole goal became one item."
- **A failed helper's log line** names the model it was given and the time it took, not "?" and 0 (worker and reviewer). This holds for every way a helper fails: a failed or empty answer, the 30-minute limit, a helper the app could not start, or a missing sub-agent service.
- **NOT DONE instead of NOT STARTED.** An item that was tried, also by helpers whose try did not count (`attempts`), and is still open is marked `[NOT DONE]` in the checklist and the report, with the reason on the line under it (or "Tried N times; not done yet."). `[NOT STARTED]` is kept for items never tried; the end reason says "N tried but not done" and "N not started" apart.

- **The run card keeps no message from an earlier run.** A button's message (End's "You ended it", for example) is cleared when a new run starts in the same thread; before, it stayed under the new run's own line (also in 1.0.0).
- **Time left stands still while paused.** The card counts from the moment of the pause ("120 min left (clock stopped while paused)"), since the deadline moves on at resume; before, it kept counting down on the card.

**Tested:** `test/helpers.test.mjs` (12 tests), each failing on the code before; `test/runbutton.test.mjs` (the two card fixes); the whole suite green (161 tests). **Lab (19 November, scripted stand-in model):** empty worker answers pause the run after three; an unusable reviewer pauses it with "The reviewer gave no usable answer"; the log names the model and time of a failed helper; the report marks a tried item NOT DONE; no new step while paused; the card shows only the new run's line. **Not verified:** a real model; a restart while paused.

## Helpers at once, parking, one writer per file, approvals parked, Depth selection (item 1, stage D, 20 November 2026)

The owner's decisions 4, 5 and 7 and points 14 to 16 (`REVIEW-REQUIREMENTS-1.md`, sections 1.3 and 1.5). Six parts. Everything from stages A to C keeps working; runs saved before (kind `mission` and `long`, without the new fields) load and run with one helper.

**1. Helpers at once.** A pool of helpers works on checklist items at the same time.
- How many: this thread's Mission settings **Helpers at once** (1 to 8; the starting value is Settings → Mission → Mission defaults → **Helpers at once**, `longHelpers`, 4). Never more than **Calls at once** for the workers' model server (`callsAtOnce`, 4 unless changed), and one at a time in a folder that keeps no checkpoints (no git, too broad or too big). It is worked out once, at the start, and kept in `run.long.helpers` (with `helpersAsked` and `helpersWhy`: '' | 'server' | 'no-checkpoints'). The start text, the Checklist view and the report say the number, and why when it is lower. Not tied to a model tier.
- 1 behaves like stage C: the same helpers, order, step texts, log lines and events; the next step starts only when the conductor calls `mission_step`.
- With more than one, the pool stays full while there is work that can move: when a helper finishes, the next ready item starts at once. The planner may give each item an `after` list (the numbers of items it needs done first); items that change the same files go one after the other.
- `mission_step` with several helpers returns what finished since the last call (several items in one answer, newest last), plus a line saying what is being worked on now. With nothing new it waits for news (a helper finishing, a park, an answer, the end) instead of answering at once.
- **Laps, checks and the review.** The overall checks, the review and a hunting lap run only when the pool has drained: no helper works while they run. A lap ends at its review, as before.
- **Item checks** run with the folder held for that moment (no file change by another helper meanwhile). A check that fails while other helpers are still working is not counted: the item is checked again on its own when they are done ("checked again when the other helpers are done"); only that result counts. A check that passes counts at once.
- **Lap undo** (the lap gate) runs inside the checks step, when the pool has drained. Items that wait for you stay waiting, marked so that their helper checks the files first when they go on.
- **Checkpoints.** The lap's checkpoint is taken once, before the lap's first change. The checkpoint after an item, and the one before a command that changes files, are taken while no other helper is changing a file. A checkpoint therefore holds the whole folder, including other helpers' unfinished work; `/mission back` to it brings that back too. While several helpers work, the checkpoint at the start of each conductor round is skipped (the conductor does no work then).
- **`/mission back` while a Mission runs** pauses it first, waits up to 10 seconds for its helpers to stop, then goes back, and says so. Resume carries on from the folder as it is.
- **Budget guard**: every helper's step counts under the thread, one 5,000-step allowance across Resume and continue. When Budget refuses a step, the Mission stops starting helpers at once, before its pause.
- **The clock**: no helper starts without time for a step (the median of measured steps); paused time is not counted; past the deadline plus the grace every helper is cut, the cut items keep their tries, and the run ends "its time was up". The time question after the plan divides the plan's minutes by the number of helpers.

At most 8 live helpers per thread; when the app refuses one more (`ACTIVATION_LIMIT_REACHED`), the helper waits and tries again for up to 10 minutes, then it is a failure that uses no try.
- **Stops**: Pause, the app's Stop, End, a hold after errors and a continue stop every helper. Their items stay open, and the next helper is told the folder may hold unfinished changes. After a restart the same is true for items a helper was working on.
- The Tool ledger records each helper's role (planner, worker, reviewer, checker, questions). Keep-awake lets go while the Mission waits for you. The report, the events and the log lines say which helper did what (`lane`, `helpers`).

**2. Parking.** A helper that needs your answer parks. The rule, as the helpers are told it:

- `NEEDS ANSWER: … | IF NO ANSWER: …` only when the item cannot be done without the answer, or a guess would mean redoing or undoing real work: it stops there. What it did is kept, the question goes to the questions card with its suggestion, and another helper takes the next item.
- `NEEDS YES: …` when a step was put to you for your yes and the item cannot be finished without it.
- `WAITING FOR FILE: …` when another helper holds a file it needs.
- From the third park of the same item it counts as a failed try, so it cannot loop.
- You can answer at any time. An answered item waits for a free helper, then a **new helper continues the kept work** (it is told what the first one reported, which files it changed, and your answer; "read those files first; do not start over"). It is not redone from scratch. Skip means: decide it yourself. A question you answered before is not asked again (stage C), and open questions with the same words are merged.
- This applies at every number of helpers (an owner question), for Missions (kind `long`). Runs of the old kind `mission` keep stage C's rule.

Then the strip says so with a clock time; after **Wait for me** it ends with its report. Finish it then takes it up again. While items wait and others work, the strip says "Running … · 2 waiting for you".

Questions with a safe default keep their default (stage C). The card after the end lists what is left; Answer and continue takes up what you answered, skipped, allowed or denied.

**5. Approvals parked** (every number of helpers, Missions of kind `long`). A helper's request for your yes never covers the chat box and never times out:

Mission counts a thread as the home mode only when Modes says so positively (`guardOf`: the space, `homeMode`, the effective mode id, and `modes.get` agrees); a read error, an unknown helper, a mismatch or no Modes counts as a guest. A Devices run carries `long.bench.home: true` only when it started as the Devices mode; if Bench later reads a guest before a check, the mark goes for good. A run saved before this fix has no mark, so its checks are fenced.
